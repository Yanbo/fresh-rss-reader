# fresh-rss-reader 实现阶段

创建日期：2026-09-09  
项目：fresh-rss-reader  
依据：doc/architecture.md 架构设计

---

## 用法

本文件把架构设计里的实现过程拆成顺序阶段，每个阶段都以一个可独立验证的行为结果为完成标志。按顺序执行时，建议在每个阶段完成后记录结果和遗留问题，便于后续阶段回看。

---

## 阶段目标和验证口径

- 每个阶段至少包含一个可见行为结果
- 前端阶段以页面/组件/交互的可见状态为准
- 后端阶段以方法可调用、数据能流转、状态能更新为准
- 集成阶段以绑定命令能触发预期行为为准

阶段之间有依赖，但每个阶段内部尽量保持自包含，避免为了“整体跑通”而拼凑。

## 阶段 1：工程初始化和前端骨架

### 目标
建立可运行的前端工程，搭好组件树和通信/状态的壳，不承载完整业务。

### 主要事项
- 用 Vite 初始化 Vue 3 项目
- 确定 `src/` 下的主要模块位置：
  - `App.vue` 作为根组件
  - `components/` 预留主要组件
  - `state/useAppState.js` 作为状态入口
  - `services/qweb.js` 作为 QWebChannel 封装
- 配好构建输出结构，让 Python 侧能加载前端产物

### 验收行为
- 本地 serve 后能打开页面
- 页面上能看到根布局/占位结构
- `services/qweb.js` 有 QWebChannel 初始化结构，不直接报初始化错误

### 产出范围
- `package.json`
- `vite.config.js`
- `index.html`
- `src/main.js`
- `src/App.vue`
- `src/services/qweb.js`
- `src/state/useAppState.js`
- `src/components/` 下的壳组件

### 注意事项
- 状态模块可以先很简单，后面再充实
- 此阶段不一定需要完整实现 Python buffer，只要前端能跑、通信结构就位就可以

---

## 阶段 2：视图组件和基本数据流

### 目标
实现 feed 列表、文章列表、文章详情三个主要视图，并能在前端展示和切换。

### 主要事项
- 实现 `FeedList.vue`
  - 渲染 feed 列表
  - 选择当前 feed
  - 已读/未读的视觉反馈
- 实现 `ArticleList.vue`
  - 渲染当前 feed 的文章
  - 选择文章
  - 已读高亮
  - 当前选中保持可见
- 实现 `ArticleView.vue`
  - 展示文章信息
  - 支持 inline 和全屏两种显示方式
  - 全屏切换由状态驱动
- 在 `useAppState.js` 中定义状态和切换函数
- 在 `App.vue` 中根据状态控制区域显隐

### 验收行为
- feed 列表和文章列表能呈现
- 选中 feed 后文章列表变化
- 选中文章后详情展示
- 全屏切换和返回列表在前端模型上能走通

### 产出范围
- `src/components/FeedList.vue`
- `src/components/ArticleList.vue`
- `src/components/ArticleView.vue`
- `src/state/useAppState.js` 的业务状态扩充
- `src/App.vue` 的布局/切换逻辑

### 注意事项
- 此阶段侧重前端模型，可暂时使用 mock 数据验证视图
- 旧 rss-reader 的“打开后找不到返回”问题，应在此阶段的状态模型里先避免：不要把详情变成不可返回的独立视图

## 阶段 3：阅读流和返回路径

### 目标
确立“打开文章 -> 全屏/inline -> 快捷键返回列表”这条核心交互流。

### 主要事项
- 实现打开文章的命令
- 实现返回列表的命令
- 快捷键 `q`（或等价键）绑定到返回逻辑
- 全屏切换命令或行为
- 文章已读标记在阅读流中的位置
- Elisp 侧将交互命令映射到 Python 方法或前端方法

### 验收行为
- 按下打开文章命令后，文章内容可见
- 在全屏或 inline 详情状态下，按返回命令后能回到列表视角
- 返回命令不依赖“猜窗口在哪”，而是基于应用状态

### 产出范围
- 前端：打开/关闭详情、全屏切换、已读标记相关的状态和方法
- Elisp：关键键绑定，至少包含返回命令和打开命令
- Python：供前端调用的打开/标记等方法，或至少的方法骨架

### 注意事项
- 这是最应该落实“更合理、更稳定”目标的阶段
- 返回路径要在状态模型和命令模型里一致，不要同一个操作在不同视图下行为不一样

---

## 阶段 4：feed 刷新、状态存储和数据持久化

### 目标
让 feed 数据能读取、刷新、保存，文章列表成为真实数据而非临时坑位。

### 主要事项
- feed 刷新实现
  - 创建/调度抓取和解析线程
  - 刷新结果送回前端
- 状态存储
  - feed 列表、文章列表持久化方式
  - 已读状态持久化
  - 考虑 JSON 或数据库作为存储介质
- 增加保存/加载逻辑，保证重启或刷新后状态合理恢复
- 前端刷新命令和刷新后的视图更新

### 验收行为
- feed 刷新后文章列表会更新
- 已读标记能落地
- 刷新/重载后，列表和选中状态不丢失或不错乱

### 产出范围
- `buffer.py` 中数据获取、刷新、存储相关的方法
- 前端刷新入口和状态更新对接
- 存储模块或存储函数的扩充

### 注意事项
- 旧版问题里曾出现“显示文章却状态错乱”的情况，新实现里应在索引/状态一致性上保持清楚
- 持久化格式和结构最好在此阶段确定，后面扩展才不会反复推翻

---

## 阶段 5：OPML 和周边管理功能

### 目标
完成标准的导入/导出能力和部分管理命令。

### 主要事项
- OPML 导入
- OPML 导出
- 添加/移除 feed 等管理命令的完善
- 与 Python 交互的方式保持一致，状态刷新及时

### 验收行为
- 从 OPML 文件导入后 feed 列表正确增加
- 导出能得到结构合理的 OPML 文件
- 添加/移除 feed 后列表和状态跟着更新

### 产出范围
- Python 侧的 OPML 处理逻辑
- 前端/Elisp 侧的导入导出入口
- 相关的列表刷新和状态更新

### 注意事项
- 此阶段可以跟数据存储阶段有重叠，但投入产出更清楚：导入/导出是一个独立的可验证能力

---

## 阶段 6：主题适配、健壮性和兼容性收尾

### 目标
让前端视觉/配色随 Emacs 主题变化，并把常见边界情况处理好。

### 主要事项
- 从 Python/Emacs 获取主题信息并传递给前端
- 前端根据主题模式调整基础样式
- 常见边界情况：
  - feed 为空
  - 文章列表为空
  - 当前文章/链接为空
  - 索引非法或越界
- 键绑定与 Doom Emacs 的兼容性检查和调整
- 错误提示和静默失败减少

### 验收行为
- 在不同主题设定下，应用的基础色彩/对比合理
- 空列表、空文章、缺失链接等情况下不出现明显破损或卡死
- 常用快捷键在 Doom Emacs 下可用且不严重冲突

### 产出范围
- 主题传递和前端样式适配代码
- 防御性校验代码
- 键绑定/配置上的调整

### 注意事项
- 这一阶段不是只做美化，核心是把不确定状态处理好，避免重演旧版里因边界情况导致的异常感受

---

## 阶段间的依赖关系

大致顺序是：

1. 阶段 1 是工程起点
2. 阶段 2 依赖阶段 1 的工程骨架
3. 阶段 3 依赖阶段 2 的视图和状态模型
4. 阶段 4 和阶段 5 在后端数据成熟后更容易完成
5. 阶段 6 最好在主要功能稳定之后再做，以免反复改样式/键绑定

如果单独验证某个阶段，会发现有的阶段在早期也能部分跑通，比如阶段 2 可以在 mock 状态下先自立，阶段 3 的命令模型也可以在视图就绪后先定义清楚，再跟后端实现对齐。

---

## 实现顺序建议

如果希望尽量减少返工，推荐顺序是：

1. 阶段 1
2. 阶段 2
3. 阶段 3
4. 阶段 4
5. 阶段 5
6. 阶段 6

这个顺序的意思是：先把视图和状态模型及返回路径建立起来，再把数据流和持久化补上，最后做导入导出和兼容性收尾。

如果希望更早看到后端数据流，也可以把阶段 4 的一部分提前，但要注意不要让前端视图连默认/空状态都没跑通就进入数据细节。
